# Changelog

## 2026-11-18: v1.9.3, decision logic property-tested on the host

- **Changed:** ✨ NEW `water_heater_monitor/detectors.h` holds the decision logic: the flash-code state machine, heating-cycle detector, hourly buckets, alert hysteresis and reading validation. It has no Arduino includes, and the `.ino` calls into it. Behaviour is unchanged apart from the fixes below, plus two harmless ones: the state machine now stamps times with the sample's `millis()` instead of a fresh `millis()` call microseconds later, and cycle durations use one `millis()` instead of four.
- **Changed:** ✨ NEW the tests drive the real C++. `tests/` compiles `detectors.h` into a host library (ctypes) and runs Hypothesis property tests against it. The old Python copy of the state machine had already drifted from the firmware, which handled pauses on a different sample and had no baseline or threshold logic. Heating-cycle detection had no tests at all.
- **Verified:** a mutation check. Six deliberate bugs were put into `detectors.h` one at a time, and each one failed at least one property: the old hourly wipe, confirming on the first pattern, removing the stall reset, steady light reading as pilot out, a blinded baseline reading as pilot out, and the cycle end needing a real drop.
- **Fixed:** the hourly heat chart was wiped when the clock stepped backwards across an hour boundary, for example an NTP correction at 14:00:01. `hour - epochHour` is unsigned, so it wrapped to a huge value and all 48 buckets were cleared. Now a backwards step leaves the buckets alone.
- **Fixed:** `/api/calibrate` saved `avg*2+50` in a uint16_t. Calibrating under a bright light (avg > 32742) stored a wrapped, tiny threshold. That calibration is now rejected with a log line and the old values are kept.
- **Fixed:** the auto threshold (threshold 0) is now computed in 32 bits. A baseline too bright for any 16-bit threshold is treated as a blinded sensor, so the status goes unknown and never pilot out. That is what the wrapped arithmetic happened to do; it is now deliberate and tested.
- **Changed:** temperature readings outside the DS18B20's −55..125 °C range are now rejected, as well as 85.0 (the power-on value). That covers the library's −127/−25x fault codes whatever DallasTemperature version is installed. 4.0.6 already maps them all to −127.
- **Measured 2026-11-18** (read-only polling of `/api/status` `light_sensor_als_raw` on v1.9.2, 40 s, code 1): each flash appears in 1–2 device samples, so the LED is on for about 150–250 ms. Flashes come every 3.0–3.2 s, so the pause is about 2.8–3.0 s. Device samples arrive about 125–136 ms apart during flashes; dark readings were all identical, so this method can't see the timing gaps between flashes. The property tests now cover 120–600 ms flashes and still pass.
- **Added:** ✨ NEW sample-gap diagnostics, to find out whether finding 1 happens in practice. Every light reading records the time since the previous one in a histogram (≤150, ≤250, ≤500, ≤1000, ≤1500, ≤3000, >3000 ms). It also tracks the longest gap and the total time spent in gaps over 250 ms. Gaps over 250 ms are long enough to miss a whole flash. Gaps over 250 ms that happen while the detector is waiting for a flash are counted separately, because those are the ones that move it towards pilot out. Exposed in `/api/debug` → `sampling`, and in the heartbeat as `gap_max_ms`, `gap_blind`, `gap_blind_wait` and `gap_blind_ms`, all cumulative since boot. These are diagnostics only: no detection decision uses them. Property-tested, and a mutation check of 4 deliberate bugs caught all four.
- **Open finding 1 (xfail test):** a false pilot out is possible when sampling is slow. If samples arrive 0.6–1.5 s apart, every 250–300 ms flash can be missed. That is slower than normal but below `FLASH_SAMPLE_GAP_MS` (1.5 s), so the stall guard doesn't fire, and code 0 gets confirmed while the LED is still flashing. Minimal case: 701 ms sampling, 250 ms flashes, 2.6 s pause. The fix depends on the LED's real on-time, which is unmeasured. The likely fix is to lower `FLASH_SAMPLE_GAP_MS` to just under the on-time (or about 400 ms).
- **Open finding 2 (xfail test):** one reading more than 2 °F above the reading 5 minutes earlier starts a heating cycle, and the next normal reading ends it, logging a ~10 s phantom cycle. A pipe can't jump 2 °F in one 10 s reading. The fix is to require the rise on 2 consecutive readings, which delays a real start by one reading. Left unchanged pending a decision.
- **Changed:** ✨ NEW sanitized for the public repo. `DEFAULT_SYSLOG_HOST` is no longer hard-coded: it comes from a gitignored `water_heater_monitor/local_config.h` (template `local_config.example.h`) and is empty without it. The web UI placeholder is `syslog.example.com`. `tools/ota-flash-when-reachable.sh` needs the device IP (argument or `WATER_HEATER_IP`) and works on Linux (`md5sum`) as well as macOS. `crash-elf/` is gitignored (core dumps can hold secrets from RAM). A new test fails if a tracked file contains an internal hostname, LAN address or personal email.
- **Impact:** v1.9.3 builds (+1032 bytes flash, +40 bytes RAM vs v1.9.2) but has not been flashed. Tests: `pytest tests/`, 35 passed (including the compile) and 2 xfailed. After flashing, let it run a day and compare heartbeat deltas of `gap_blind_wait`. If it's about 0, finding 1 is theoretical. If it's frequent, the planned fix ("don't count blind time towards pilot out") is needed before `FLASH_SAMPLE_GAP_MS` can safely be lowered.

## 2026-10-30: v1.9.2, motion sensing off by default

- **Changed:** Wi-Fi CSI motion screen-off now defaults to disabled, and its config option warns that it may cause reboots.
- **Why:** boots rose from 1 in 14 days to about 19 in 4 days after CSI arrived in v1.8.0, and v1.9.1 still crashed. The decoded dump shows a jump to address 0 from `wDev_ProcessFiq` (Wi-Fi driver interrupt) while `ppTask` was in `wDev_IndicateFrame`. None of this project's code was on the stack, so this is a strong correlation, not a proven root cause.
- **Impact:** the display stays on all the time. Devices that already saved the setting keep their saved value.
